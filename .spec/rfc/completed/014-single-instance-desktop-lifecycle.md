# RFC 014：Velox Desktop 单实例生命周期

**状态**：已完成
**创建日期**：2026-07-27
**最后更新**：2026-07-28
**作者**：CleanSpace
**依赖**：[RFC 013](./completed/013-velox-ui-shell-migration.md)

---

## 摘要

CleanSpace Velox Desktop 在同一 macOS 用户会话中只允许一个运行实例。再次启动时，新进程不创建窗口、不初始化 Velox Runtime，而是唤醒已有主窗口后正常退出。

SwiftUI 菜单栏辅助进程不属于本 RFC 的互斥范围，必须继续允许与 Velox Desktop 同时运行。

## 问题

`apps/desktop/desktop-velox/Sources/CleanSpaceDesktop/main.swift` 当前直接调用 `DesktopApp.run()`。通过开发脚本或直接执行二进制时，Launch Services 不保证替应用完成进程级去重，因此多个 Desktop 进程可同时创建 WebView、采样系统指标并启动扫描任务。

这不是窗口数量问题。Velox 配置只有一个主窗口，但多个进程仍各自拥有一个主窗口。唯一性必须建立在进程生命周期入口，不能靠 React 状态或窗口枚举修补。

## 目标

1. 同一用户会话中最多存在一个 Velox Desktop 主实例。
2. 第二次启动须唤醒、恢复并置前已有主窗口。
3. 第二实例须在加载 `velox.json`、创建 WebView、注册 IPC 前退出。
4. 主实例正常退出或崩溃后，锁须由操作系统自动释放。
5. `pnpm run:swiftui` 启动的 SwiftUI 辅助进程不受影响。
6. 开发运行与打包应用使用相同单实例语义。

## 非目标

- 不把 SwiftUI 辅助进程并入同一互斥域。
- 不实现跨用户会话互斥。
- 不传递文件打开、URL Scheme 或任意命令行载荷。
- 不修改 React、IPC 命令、扫描协调器或业务数据。
- 不依赖仅对 `.app` 双击启动有效的 Launch Services 行为。

## 方案比较

### 方案 A：查询 `NSRunningApplication`

启动时按 bundle identifier 查询已有进程；存在则激活并退出。

优点：代码少，只用 AppKit。

缺点：查询与继续启动之间存在竞态。两个同时启动的进程可能都查询不到对方，然后同时成为主实例。此方案不满足唯一性保证。

### 方案 B：内核文件锁 + 分布式唤醒通知

启动时对固定、用户级锁文件执行非阻塞排他锁。抢锁成功者成为主实例并持续持有文件描述符；失败者发送只包含“激活主窗口”语义的分布式通知后退出。

优点：内核负责互斥；进程异常终止后自动释放；通知与锁职责分离；实现和测试边界清楚。

缺点：锁文件会持久存在；必须保证主实例长期持有文件描述符；唤醒通知属于 macOS 平台实现。

### 方案 C：Unix Domain Socket 或 `CFMessagePort`

以唯一端点同时承担选主与消息传递。

优点：未来可扩展到传递打开文件或命令行载荷。

缺点：端点清理、连接错误、RunLoop 接线与测试成本更高。当前需求没有载荷传递，属于过度设计。

## 决策

采用方案 B。

互斥与唤醒是两件事：

- 文件锁只回答“谁是主实例”。
- 分布式通知只表达“请激活已有窗口”。

不得用进程列表、PID 文件是否存在或窗口列表代替内核锁。这些方案都把竞态重新引入启动路径。

## 技术设计

### 1. 生命周期协调器

在 `CleanSpaceDesktopRuntime` 新增 macOS 专用 `SingleInstanceCoordinator`。协调器拥有：

- 稳定的 Velox Desktop 实例标识。
- 已打开锁文件的文件描述符。
- 主实例使用的分布式通知观察者。
- 主窗口激活回调。

启动结果只有两种正常状态：

| 状态 | 含义 | 后续行为 |
|------|------|----------|
| `primary` | 当前进程取得排他锁 | 注册唤醒观察者，继续启动 Velox |
| `secondary` | 已有进程持有排他锁 | 发送唤醒通知，返回入口并退出 |

打开锁文件、创建父目录或注册观察者失败属于启动错误，必须携带底层错误信息；不得静默退化为多实例运行。

### 2. 锁身份与所有权

锁文件使用 Velox Desktop Bundle 标识 `me.systembug.cleaning`，并放在当前用户可写、不同用户隔离的运行目录。

规则：

1. 使用原子、非阻塞排他锁。
2. 主实例持有同一个文件描述符直到进程退出。
3. 运行期间不得删除锁文件。删除后重新创建会产生不同 inode，可能形成两个主实例。
4. 不把 PID 内容当作锁真相；锁状态由内核决定。
5. SwiftUI 辅助进程不调用此协调器，也不共享该标识。

### 3. 启动顺序

`DesktopApp.run()` 的顺序固定为：

1. 确认主线程。
2. 创建并保留 `SingleInstanceCoordinator`。
3. 尝试成为主实例。
4. 若为第二实例，发送唤醒通知并立即返回。
5. 若为主实例，注册唤醒处理。
6. 执行图标加载、配置读取、事件接线、协议注册与 Velox Runtime 启动。

协调器必须由 `DesktopApp` 以进程生命周期级别强引用。局部变量离开作用域后释放文件描述符会让互斥失效。

### 4. 唤醒已有窗口

主实例收到通知后，在主线程执行：

1. 激活当前应用。
2. 若主窗口最小化，恢复窗口。
3. 将主窗口置前并设为 key window。

通知不得携带路径、命令或其他不可信载荷。外部进程伪造通知最多导致窗口置前，不得触发清理、扫描或 IPC。

### 5. 退出语义

第二实例不是崩溃，也不是配置错误。它完成唤醒通知后从 `DesktopApp.run()` 返回，进程以成功状态结束。

主实例的现有 `.windowCloseRequested` 与 `.userExit` 退出策略保持不变。进程结束后，内核释放排他锁；下次启动可成为新主实例。

## 测试策略

先写失败测试，再实现生产代码。

### 自动化测试

`CleanSpaceDesktopRuntimeTests` 至少覆盖：

1. 第一个协调器可取得给定测试锁。
2. 同一锁上的第二个协调器被判定为第二实例。
3. 主协调器释放后，新协调器可以成为主实例。
4. 第二实例路径只发送一次唤醒请求。
5. 主实例路径不会发送唤醒请求。
6. 锁目录或锁文件打开失败时返回明确错误，不继续启动。

测试使用唯一临时锁路径和注入式通知发送器，避免污染真实应用锁。窗口激活行为通过窄回调边界验证；不在单元测试中启动真实 Velox EventLoop。

### 手动验收

1. 启动 Velox Desktop，记录进程数与主窗口。
2. 再次启动同一二进制，确认仍只有一个 Velox Desktop 进程。
3. 最小化主窗口后再次启动，确认原窗口恢复并置前。
4. 隐藏应用后再次启动，确认应用激活。
5. 强制终止主实例后重新启动，确认可正常取得锁。
6. 同时运行 Velox Desktop 与 `pnpm run:swiftui`，确认两者均保持运行。

## 风险与缓解

| 风险 | 缓解 |
|------|------|
| 协调器过早释放 | `DesktopApp` 进程级强引用；释放后重获锁测试 |
| 同时启动竞态 | 内核非阻塞排他锁，不使用查询后判断 |
| 锁文件残留被误判 | 判断锁状态，不判断文件是否存在 |
| 运行中删除锁文件产生双实例 | 永不主动删除锁文件 |
| 通知到达后台线程 | 激活逻辑显式切回主线程 |
| 唤醒通知被伪造 | 通知无载荷，只允许无副作用窗口激活 |
| SwiftUI 辅助进程被误杀 | 独立入口、独立标识，不参与该锁 |

3. `TASK-014-03`：在 `DesktopApp.run()` 最前端接入并保持协调器生命周期。

## 验收标准

1. 自动化测试覆盖锁获取、竞争、释放、通知与错误路径。
2. 第二实例不读取 Velox 配置、不注册协议、不创建 WebView。
3. 双启动后只有一个 Velox Desktop 进程。
4. 已有主窗口从最小化或隐藏状态恢复并置前。
5. 主进程异常终止后不遗留逻辑死锁。
6. SwiftUI 辅助进程可与 Velox Desktop 同时运行。
7. `pnpm test:swift` 与相关构建检查通过。

## 回滚

删除 `DesktopApp.run()` 的协调器接线及新增运行时文件、测试即可恢复原行为。锁文件没有业务数据，不需要迁移或清理。

## 待批准事项

本 RFC 批准后才可修改运行代码。批准即冻结以下选择：

- 仅约束 Velox Desktop。
- 采用内核文件锁选主。
- 采用无载荷分布式通知唤醒主窗口。
- 不扩展到文件或 URL 转发。
