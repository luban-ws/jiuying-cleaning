# RFC 009：用户规则安全边界与路径/命令约束

**状态**：已完成  
**创建日期**：2026-04-12  
**作者**：CleanSpace  
**依赖**：[RFC 001](../001-ccleaner-style-cleaning-spec.md) 安全与校验。

**调用方（依赖本 RFC，而非反向依赖）**：[RFC 005](../005-user-rules-yaml-and-settings-editor.md)（保存/加载）、[RFC 006](../006-rules-import-and-export.md)（导入）、内置与用户规则统一加载器。

**实现进度**：`UserRuleValidator` + `CleaningRulesLoader.loadUserRules(from:policy:)` + `UserRuleValidatorTests` + [argv 白名单文档](../../../docs/user-rule-command-whitelist.md)（TASK-009-01/02/03 核心）；保存/导入接线随 RFC 005/006 复用同一入口；`exclude` / `minSizeBytes` 明确推迟到后续 Phase 2，不属于本次完成口径。

---

## 摘要

用户规则与导入文件可能包含危险 `base` 或任意 shell 命令。本 RFC 规定：**路径在用户域内的规范解析（含符号链接）**、**命令可执行文件 / argv 白名单**（**禁止**以复杂正则作为主要安全机制）、默认风险等级、以及与预览/确认文案的联动。可选地定义规则级 **exclude** 或「仅超过阈值的子目录」以支持 001 中「仅大项」方向（若 v1 不做 exclude，须在正文明确推迟）。

---

## 背景与问题

- RFC 001 要求禁止 `/System`、`/usr` 等；用户规则 `~` 展开后仍可能拼出越界路径。
- `type: command` 若允许任意字符串，等同于本地 RCE 入口（虽由用户自己导入，仍应纵深防御）。

---

## 范围

**在本 RFC 内**

- **单一校验模块**：在加载、保存、导入时运行；**失败策略定案**：**按条拒绝**（跳过非法条并汇总错误；若文件级无法部分解析则拒绝整文件——YAML/JSON 解析失败属整文件拒绝）。加载器、编辑器、导入 UI **共用**同一校验入口，禁止在 UI 层复制规则。
- **路径（定案）**：`~` 或等价主目录展开后，对路径做 **规范解析（解析符号链接后的真实路径）**；**最终路径须位于** `NSHomeDirectory()` 下**预先允许的子树前缀列表**内（如 `.../Library/...`、`.../Downloads/...` 等，完整列表在实现中数据驱动并附单元测试）。**拒绝**：解析后落在 `/System`、`/usr`、系统 `/Library`、其他用户目录等。**符号链接**：若解析后逃出用户允许前缀，**拒绝该规则**（与 [RFC 003](./003-chromium-profile-discovery.md) profile 目录逃逸处理一致）。
- **命令（定案）**：**禁止**将「宽泛正则匹配整条 command 字符串」作为主要防线。采用分层校验：
  1. **可执行文件白名单**：仅允许解析后的 **argv[0]** 为列表中项（如 `/usr/local/bin/docker`、`/opt/homebrew/bin/docker` 等，随实现维护列表）；或
  2. **固定子命令表**：在 argv[0] 已白名单前提下，**仅允许**第二段及后续为文档化子命令前缀（如 `docker system prune` 的允许 token 序列），用 **token 级比对** 而非整条 shell 正则。
  **不在白名单**：**禁止保存**用户规则与导入（不采用「标记 high 仅二次确认即可任意命令」的宽松模式，以降低 RCE 面）。内置规则中的命令类项不受本「用户规则」条限制，但须单独 code review。

**可选（明确推迟）**

- Schema 扩展：`exclude` 子路径列表；或 `minSizeBytes` 仅清理超过阈值的直接子项。当前完成口径不扩展 schema，避免把用户规则安全基线和扫描/清理语义绑在一起；后续如需要，另开 Phase 2 任务并补扫描、预览、清理一致性测试。

**不在本 RFC 内**

- 沙箱内执行命令（若未来需要，另开 RFC）。

---

## 提案要点

1. 与 [RFC 004](./004-full-disk-access-onboarding.md) 区分：本 RFC 管「规则是否**合法**」，004 管「系统是否**允许读**」。
2. **扩展流程**：新增允许的 `docker` 子命令或其它 argv[0] 须 **PR + 文档** 更新白名单表；禁止仅在生产配置中静默加宽。

---

## 验收标准

- 单元测试覆盖：**越界路径**、**主目录内符号链接逃逸**（指向 `/etc` 等）、**危险命令**（未白名单 argv[0]、注入式 `; rm` 拼接若解析为 shell 则须不存在——用户规则 command 应以 **argv 列表** 存储若 schema 支持，否则须文档说明如何安全拆分）、**边界合法的 `~/Library/...` 规则**。
- 文档列明 **argv[0] 白名单**、**允许的 docker（或其它）子命令前缀表** 与扩展流程（如何申请新增）。

---

## 与 RFC 001 的关系

落实 001「安全与校验」中可编码的部分，使 005/006 有统一安全基线。
