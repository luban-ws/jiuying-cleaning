# RFC 007：清理操作审计日志

**状态**：草案  
**创建日期**：2026-04-12  
**作者**：CleanSpace  
**依赖**：[RFC 001](./001-ccleaner-style-cleaning-spec.md) 实现要点（记录操作便于审计）

---

## 摘要

每次用户确认并执行清理后，将**结构化记录**追加到本机日志（时间、规则 id、类型、成功/失败摘要、可选命令退出码）。**不**在本 RFC 内承诺「撤销已删文件」；若未来支持撤销，须另开 RFC。

---

## 背景与问题

- 用户需要回答「我上次到底清了什么」；企业场景需要审计轨迹。
- RFC 001 脚注提到撤销可单独 RFC，本 RFC 明确边界以免范围膨胀。

---

## 范围

**在本 RFC 内**

- 日志存储位置：例如 `~/Library/Application Support/CleanSpace/audit.log` 或按日轮转文件；格式为 JSON Lines 或等价可解析格式。
- UI：**可分阶段**：Phase 1 仅可靠追加日志文件；Phase 2 在规则页或设置中提供「最近操作」列表（只读）、可清空（需二次确认）。若 Phase 1 无 UI，须在设置或关于页提供「审计日志路径」说明，便于高级用户自行查看。
- **隐私（定案）**：不记录文件内容。**默认**每条记录以 **规则 `id`、类型、时间戳、成功/失败摘要、命令退出码（若有）** 为主；**完整文件系统路径为可选**，默认关闭，若开启须在设置中显式开关并附简短隐私说明（路径可能暴露用户名与目录结构）。

**不在本 RFC 内**

- 撤销（undelete）、Time Machine 集成。
- 云端上传。

---

## 提案要点

1. 与 Docker 命令类规则一致，失败时记录 stderr 摘要（长度上限）。
2. 日志写入失败**不得阻塞**清理主流程，且**不得静默无声**：至少 **递增持久化或内存中的 `auditWriteFailureCount`**、写入 **`os_log`（或等价）一条可检索错误**，并在 **设置 → 关于/诊断**（或等价入口）向用户展示「最近审计写入失败次数」或一次性横幅（实现选一定案，须在帮助中说明）。禁止「失败即丢、无计数、无日志」。
3. 审计写入与清理执行宜抽象为 **「一次用户确认清理 = 一条审计事务」** 的接口，避免散落在各删除调用点。

---

## 验收标准

- 执行一次 dry-run **不**写审计（**须**有单元测试或逻辑测试钉死该行为，防止回归为「顺便记一笔」）。
- 执行一次真实清理产生一条可追溯记录（在默认隐私模式下含 `id`，不含完整路径，除非开启可选开关）。
- 单元测试可注入临时目录验证追加格式；**模拟日志目录不可写**时，断言 **清理仍完成** 且 **失败计数或 `os_log` 侧可观测行为** 之一成立（若 CI 无法断言 log，则断言内存/持久计数递增并在测试内可读）。
