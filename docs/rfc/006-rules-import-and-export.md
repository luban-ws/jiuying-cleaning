# RFC 006：清理规则导入与导出

**状态**：草案  
**创建日期**：2026-04-12  
**作者**：CleanSpace  
**依赖**：[RFC 001](./001-ccleaner-style-cleaning-spec.md) 共享与复用；[RFC 005](./005-user-rules-yaml-and-settings-editor.md)（导出对象以用户规则为主）；[RFC 009](./009-user-rule-safety-and-exclusions.md)（导入前**必须**通过 009 校验）。**推荐交付顺序**：009 与用户规则加载路径就绪后，再默认开放「从文件导入」以降低恶意/错误规则扩散风险。

---

## 摘要

便于团队与社区共享规则：支持将规则集**导出**为文件，以及从文件**导入**到用户规则存储区，并处理 `id` 冲突与合并策略。**默认合并策略定案为保守**，避免静默覆盖用户已有规则。

---

## 背景与问题

- 复制粘贴 JSON 易错；需要明确「导入是替换还是合并」。
- RFC 001 要求可共享、可版本管理。

---

## 范围

**在本 RFC 内**

- **导出格式定案（v1）**：`UTF-8` 编码的 **JSON 数组**，元素为与 001 schema 一致的单条规则对象；文件扩展名建议 `.cleanrules.json` 或 `.json`（实现选一定死并写入帮助）。YAML 导出若需，列为 Phase 2，不在 v1 承诺范围。
- 导入流程：先经 **RFC 009** 校验；再展示预览（将新增 / **将与本地冲突的 `id`**）；默认确认后执行 **保守合并**（见下节「合并策略」）。
- 可选：从剪贴板导入单条规则（同样走 009 + 预览）。

**不在本 RFC 内**

- 云端同步、签名规则包（另开 RFC）。

---

## 合并策略（定案）

实现上将「合并」实现为**可替换策略**（便于将来团队策略、签名包），但 **v1 默认策略**如下：

| 模式 | 行为 |
|------|------|
| **默认导入**（主按钮） | **仅追加**文件中**本地尚不存在**的 `id`；对本地已存在的 `id`，**跳过导入文件中的对应条**并在预览中列出「冲突已跳过」，**不修改**本地该条规则。 |
| **高级：覆盖冲突 `id`**（次要入口，须额外确认） | 对预览中冲突的 `id`，用导入文件版本**替换**本地对应条；仍须通过 009。 |

不得默认静默覆盖；「整文件替换」若提供，须独立危险确认（等同清空用户规则再导入），建议 v1 不暴露或隐藏在开发者选项。

## 提案要点

1. 导入前 **schema + RFC 009** 安全校验；失败则拒绝整文件或拒绝单条（与 009 定案一致）。
2. 导出不应包含本机绝对路径中的敏感信息；若规则含 `~` 则保持 `~` 前缀；避免导出运行时展开后的绝对路径列表（除非用户显式选择「展开路径」类高级选项且另开确认）。
3. **测试矩阵（建议）**：`id` 冲突且 body 不同、`id` 相同且 body 相同、导入文件出现新 `id` 与本地无交集——三种情况合并结果须有自动化或快照测试覆盖。

---

## 验收标准

- 导出再导入后，规则列表与合并结果符合 **默认保守策略** 与 **可选覆盖策略**（集成测试或快照测试）。
- 文档说明与 005 编辑器如何配合（按钮入口位置）。

---

## 与 RFC 001 的关系

落实 001「导入/导出」能力，不扩展规范外的规则字段。
